# GPIO Button Interrupt 🐈

This example toggles the onboard red LED each time the onboard push button is pressed using a Port 1 interrupt.

Unlike the previous GPIO examples, the program does not continuously poll the button inside the main loop. Instead, the MSP432P401R responds to the button press by executing an interrupt service routine.

---

## 1. Overview

The onboard push button connected to `P1.1` is configured as an active-low GPIO input with an internal pull-up resistor.

When the button is pressed, `P1.1` transitions from logic high to logic low. This falling edge generates a Port 1 interrupt.

The processor then temporarily stops executing the main program, runs the Port 1 interrupt service routine, toggles the onboard red LED connected to `P1.0`, and returns to the main program.

This example introduces:

* GPIO interrupts
* Falling-edge detection
* Interrupt flags
* Peripheral interrupt enable
* NVIC interrupt enable
* Global interrupt enable
* Interrupt service routines
* Basic interrupt debouncing

## 3. Pinout / Wiring

The LED and push button are already connected to the MSP432P401R LaunchPad.

| Component   | MSP432P401R Pin | Configuration                    |
| ----------- | --------------- | -------------------------------- |
| Red LED     | `P1.0`          | GPIO output                      |
| Push Button | `P1.1`          | GPIO input with internal pull-up |

The onboard button is connected so that:

| Button State | P1.1 Input |
| ------------ | ---------- |
| Released     | Logic `1`  |
| Pressed      | Logic `0`  |

Because the input becomes low when the button is pressed, the button is **active-low**.

## 4. Code Walkthrough

### 4.1 Configure the LED and Button

The red LED and push button are initialized using separate functions:

```c
LED_initializeRedLED();
Button_initializeOnBoardButton();
```

Using initialization functions keeps `main()` focused on the overall program flow while the register configuration remains organized in dedicated functions.

The LED is configured as a GPIO output, while the button is configured as a GPIO input with its internal pull-up resistor enabled.

---

### 4.2 Select the Interrupt Edge

```c
P1->IES |= BIT1;
```

The `IES` register selects which signal transition generates an interrupt.

For the Port 1 interrupt edge selection:

| IES Bit | Interrupt Edge |
| ------- | -------------- |
| `0`     | Low-to-high    |
| `1`     | High-to-low    |

The `P1.1` button uses an internal pull-up resistor:

```text
Released → HIGH
Pressed  → LOW
```

Therefore, pressing the button creates a:

```text
HIGH → LOW
```

transition.

Setting bit 1 in `P1->IES` configures `P1.1` to generate an interrupt on this falling edge.

---

### 4.3 Clear the Interrupt Flag

```c
P1->IFG &= ~BIT1;
```

The `IFG` register contains interrupt flags.

When the configured interrupt condition occurs on a pin, the corresponding flag is set.

For this example:

```text
P1.1 falling edge
        ↓
P1IFG.1 becomes 1
        ↓
Port 1 interrupt request
```

The flag is cleared before enabling the interrupt to make sure that a previously pending flag does not immediately trigger the interrupt handler.

The flag must also be cleared after handling the interrupt so the next button press can be detected correctly.

---

### 4.4 Enable the P1.1 Interrupt

```c
P1->IE |= BIT1;
```

The `IE` register controls whether an individual GPIO pin is allowed to generate an interrupt.

Setting bit 1 enables interrupt generation for `P1.1`.

At this point, the GPIO peripheral is configured to detect the button press, but the processor still needs to be configured to accept the Port 1 interrupt.

---

### 4.5 Enable Port 1 in the NVIC

```c
NVIC_EnableIRQ(PORT1_IRQn);
```

The MSP432P401R uses an ARM Cortex-M4F processor with a **Nested Vectored Interrupt Controller**, commonly called the **NVIC**.

The NVIC controls which processor-level interrupt sources are enabled.

`PORT1_IRQn` identifies the Port 1 interrupt inside the NVIC.

Calling:

```c
NVIC_EnableIRQ(PORT1_IRQn);
```

allows the NVIC to accept interrupt requests generated by Port 1.

There are therefore two levels of interrupt enable involved in this example:

```text
P1->IE
   ↓
Enable the individual GPIO pin interrupt

NVIC_EnableIRQ(PORT1_IRQn)
   ↓
Enable the Port 1 interrupt at the processor level
```

Both are required.

---

### 4.6 Enable Interrupts Globally

```c
__enable_irq();
```

Even after the GPIO interrupt and NVIC interrupt are enabled, the processor must still allow interrupts globally.

`__enable_irq()` clears the processor's global interrupt mask and allows enabled interrupt requests to be serviced.

The interrupt configuration can be viewed as three levels:

```text
P1->IE
    ↓
Enable P1.1 interrupt

NVIC_EnableIRQ(PORT1_IRQn)
    ↓
Enable Port 1 in the NVIC

__enable_irq()
    ↓
Allow the CPU to respond to interrupts
```

If any of these levels is disabled, the interrupt service routine will not execute.

---

### 4.7 Main Loop Without Polling

```c
while (1)
{
    /*
     * No polling is required here. Button presses are handled by
     * the Port 1 interrupt service routine.
     */
}
```

The main loop does not continuously check the button state.

This is the main difference between this example and the earlier GPIO polling example.

### Polling

```text
Main loop
   ↓
Read button
   ↓
Pressed?
   ↓
Read button again
   ↓
Repeat continuously
```

The processor repeatedly checks the input even when nothing is happening.

### Interrupt

```text
Main program
   ↓
Button press occurs
   ↓
Interrupt request
   ↓
PORT1_IRQHandler()
   ↓
Handle button press
   ↓
Return to main program
```

The button itself causes the processor to execute the interrupt handler.

This allows the main program to perform other work instead of constantly checking the input.

---

### 4.8 Port 1 Interrupt Service Routine

```c
void PORT1_IRQHandler(void)
```

An interrupt service routine, or **ISR**, is a function that executes when its associated interrupt occurs.

`PORT1_IRQHandler()` is the interrupt handler associated with Port 1.

The function name is important because the MSP432 startup code and interrupt vector table expect this specific handler name for the Port 1 interrupt.

When a Port 1 interrupt occurs, the processor automatically transfers execution to this function.

---

### 4.9 Check the Interrupt Source

```c
if ((P1->IFG & BIT1) != 0U)
```

A single port can contain several GPIO pins capable of generating interrupts.

The interrupt handler therefore checks the interrupt flag to determine which pin generated the request.

This example only uses `P1.1`, so the handler checks bit 1 of `P1->IFG`.

If the bit is set, the interrupt was generated by the button.

This becomes especially useful when multiple pins on the same port use interrupts.

---

### 4.10 Toggle the LED

After the button press is detected, the red LED is toggled:

```c
P1->OUT ^= BIT0;
```

The XOR operator reverses the current state of `P1.0`.

| Current State | New State |
| ------------- | --------- |
| `0`           | `1`       |
| `1`           | `0`       |

Therefore, each valid button interrupt changes the LED from:

```text
OFF → ON
```

or:

```text
ON → OFF
```

No separate LED state variable is required because the current state is already stored in the output register.

---

### 4.11 Button Debouncing

```c
__delay_cycles(BUTTON_DEBOUNCE_DELAY_CYCLES);
```

Mechanical push buttons can rapidly alternate between high and low for a short period when their contacts close or open.

This behavior is called **button bounce**.

A short delay is used inside the interrupt handler to reduce the chance of multiple interrupt events being treated as separate button presses.

This is a simple debounce method intended for an introductory example.

In larger embedded systems, long delays inside interrupt service routines are generally avoided because the processor remains inside the ISR during the delay.

More advanced approaches can use timers or additional state logic to debounce the button without blocking inside the interrupt handler.

---

### 4.12 Clear the Interrupt Flag

Before leaving the interrupt handler, the `P1.1` interrupt flag is cleared:

```c
P1->IFG &= ~BIT1;
```

Clearing the flag indicates that the interrupt has been handled.

The processor can then respond to the next valid button press.

A useful simplified interrupt sequence is:

```text
Button press
     ↓
P1.1 falling edge
     ↓
P1IFG.1 set
     ↓
Port 1 interrupt requested
     ↓
NVIC sends interrupt to CPU
     ↓
PORT1_IRQHandler()
     ↓
Toggle LED
     ↓
Clear P1IFG.1
     ↓
Return to main program
```

---

## 5. Expected Result

After programming the MSP432P401R LaunchPad:

1. The onboard red LED begins turned off.
2. Press the onboard button connected to `P1.1`.
3. The red LED turns on.
4. Release the button.
5. Press the button again.
6. The red LED turns off.

Each valid button press toggles the LED once.

The main program does not continuously poll the button.

## 7. Common Problems

### Pressing the button does nothing

Verify that:

* `P1.1` is configured as a GPIO input.
* The internal resistor is enabled.
* The pull-up resistor is selected.
* The `P1.1` interrupt is enabled using `P1->IE`.
* Port 1 is enabled in the NVIC.
* Global interrupts are enabled.

All interrupt enable levels must be configured correctly.

### The interrupt occurs immediately after startup

A pending interrupt flag may already be set before the interrupt is enabled.

Make sure the `P1.1` flag is cleared before enabling the interrupt:

```c
P1->IFG &= ~BIT1;
```

### The button only works once

Verify that the `P1.1` interrupt flag is cleared inside the interrupt service routine after the button press is handled.

If the flag is not cleared correctly, future button events may not behave as expected.

### The interrupt occurs when the button is released instead of pressed

Check the `P1->IES` configuration.

The onboard button uses an internal pull-up resistor, so pressing the button creates a high-to-low transition.

The interrupt should therefore be configured for a falling edge.

### The LED toggles multiple times from one press

Mechanical button bounce may generate additional transitions.

This example uses a short software delay to reduce bounce. Increasing the debounce delay slightly may help if the button still produces multiple toggles.

### The button worked with polling but not with interrupts

Polling only requires reading the GPIO input.

Interrupt operation additionally requires:

* Interrupt edge configuration
* Interrupt flag handling
* GPIO interrupt enable
* NVIC interrupt enable
* Global interrupt enable
* A correctly named interrupt service routine

Check each part of the interrupt path individually.
